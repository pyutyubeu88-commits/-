# 네이버 블로그 완전자동화 리서치 — Claude + 텔레그램 + Codex

## 결론부터

**"완전 무인 자동화"는 기술적으로는 가능하지만 사업적으로는 금지한다.**
네이버 계정 정지 리스크가 얻는 이득보다 훨씬 크기 때문이다. 대신 **"체감상 완전자동, 실질은 사람이 딱 두 곳(로그인·발행)만 남는 반자동"**을 목표로 잡는다.

또한 리스크 관리에만 집중하면 반쪽짜리 기획이 된다. **진짜 병목은 발행 버튼(10초)이 아니라 소재 발굴·카피라이팅·채널별 중복작업**이다. 이 문서 후반부(6번)에서 그 레버리지를 추가로 다룬다.

## 0. 팩트 체크

- 네이버 **"글쓰기 API"는 2020년 5월 6일 공식 종료**됐다. 종료 사유가 결정적이다 — 사용자가 로그인 없이 워드프로세서나 웹 노트에서 작성한 글을 API로 블로그에 대량 게재하는 어뷰징(광고성 블로그 양산)이 문제가 되어 서비스 시작 10년 만에 네이버가 직접 껐다. ([뉴시스](https://www.newsis.com/view/NISX20200413_0000992012), [뉴스핌](https://www.newspim.com/news/view/20200413000737))
- 이는 "자동 발행 패턴"이 네이버 FDS가 **이미 한 번 실제로 대응한 전례가 있는 타겟**이라는 뜻이다. 브라우저 자동화로 이를 재현하려는 시도는 종료된 API가 하던 일을 비공식 경로로 다시 하는 것과 같아서 리스크가 더 높아졌으면 높아졌지 낮아지지 않았다.
- "이메일로 포스팅" 등 우회 가능한 공식 자동화 채널은 검색으로 확인되지 않았다 — 없다고 보고 설계한다.
- 반면 **네이버 데이터랩(DataLab)·검색광고 API는 읽기 전용 공식 API로 현재도 정상 운영 중**이다. 자동화는 "쓰기(발행)"가 아니라 "읽기(키워드 리서치)" 쪽에 걸어야 안전하고 지속 가능하다.

---

## 1. 왜 완전 무인이 안 되는가

- 네이버는 개인이 블로그 글을 발행할 수 있는 **공식 오픈 API가 없다** (네이버 오픈API는 검색/읽기 위주).
- 자동 로그인 + 자동 글쓰기는 이용약관 위반이자 **부정이용탐지(FDS)의 1순위 타깃**이다. 새 기기·새 IP에서 로그인하면 캡차·2단계인증(SMS)이 거의 확정적으로 뜬다 — 이건 우회 대상이 아니라 사람이 개입해야 하는 지점이다.
- 에디터(SmartEditor ONE)는 iframe·동적 DOM이라 셀렉터가 자주 깨져 **유지보수 비용이 상시 발생**한다.
- 최악의 경우 **클라이언트 계정 영구정지** → 컨설팅 사업 자체가 끝나는 사고. 리스크 대비 이득이 비대칭적으로 나쁘다.

## 2. 아키텍처 옵션 비교

| 항목 | (a) 완전무인 | (b) 반자동 + 텔레그램 승인 | (c) 초안까지만 자동 |
|---|---|---|---|
| 계정정지 리스크 | 매우 높음 | 낮음 (수동 발행이라 0) | 없음 |
| 유지보수 비용 | 높음 (셀렉터 상시 깨짐) | 중간 | 낮음 |
| 실패 모드 | 캡차·정지·오발행 | 봇 다운 (치명적 아님) | 거의 없음 |
| 다수 클라이언트 확장 | 불가 (계정마다 정지위험 누적) | **가능** | 가능 |
| 사람 부담 | 0 (단, 사고 시 무한대) | 승인 1클릭 | 복붙 발행 |

**채택: (b)를 기본으로, 발행 단계만 (c)처럼 반수동 처리하는 하이브리드.**

## 3. 텔레그램의 역할 — 단순 알림이 아니라 컨트롤 플레인

명령 + 승인 인터페이스로 쓴다.

```
/포스팅 역삼효태권도장
  → Claude가 초안 생성
  → 미리보기 카드 + 인라인 버튼(발행준비 / 수정요청 / 폐기)
  → 컨설턴트 승인
  → "발행" 버튼은 자동 로그인을 트리거하지 않는다.
     클립보드/임시저장으로 넘기는 데까지만 한다.
```

클라이언트별 봇을 따로 만들 필요는 없다(과잉설계) — **채팅방/스레드 구분**으로 충분하다.

## 4. Codex CLI의 실제 역할

Codex는 **실행기가 아니라 개발 도구**다.

- ✅ 맞는 쓰임: 텔레그램 봇 서버, 초안 생성 파이프라인, 임시저장 보조 스크립트를 **짜고 유지보수**하는 코딩 에이전트로 활용
- ❌ 틀린 쓰임: Codex 에이전트가 런타임에 직접 브라우저를 몰아 네이버에 로그인·발행하는 방식 — 비결정적이고 느리고 탐지에 더 취약해서 기각

## 5. 최종 권장 파이프라인 (1인 운영, 상시 서버 불필요)

1. **트리거**: 텔레그램 `/포스팅 [클라이언트명]` 또는 Vercel Cron (주 1회 배치 권장, 6번 참고)
2. **키워드 리서치**: 네이버 데이터랩·검색광고 API(공식, 읽기전용)로 실제 검색량 있는 키워드 자동 수집
3. **생성**: Claude API가 (업종별 템플릿 + 키워드 데이터를 입력으로) 주제·본문·이미지 프롬프트를 생성 — 이때 블로그뿐 아니라 인스타 카드뉴스·쇼츠 대본·카카오문자까지 한 번에 원소스 멀티채널로 생성
4. **초안 전달**: 텔레그램으로 후킹 표지문구 + 본문 + 저장유도 CTA 미리보기 + 인라인 버튼
5. **사람 게이트**: 컨설턴트가 검수 → 승인 (배치로 모아서 주 1회 처리)
6. **반수동 발행**: 승인 시 본문을 모바일 네이버 앱 임시저장/클립보드로 전달 → 사람이 앱에서 최종 발행, 이때 네이버 앱 네이티브 **예약발행** 기능으로 발행 시각까지 지정 (정상 세션이라 FDS 안전)
7. **성과 피드백**: 발행 후 조회수·저장수를 간단히 기록 → 다음 회차 키워드/주제 선정에 반영
8. **인프라**: Vercel Serverless Functions + 텔레그램 Webhook만으로 성립, 상시 서버 불필요

**사람이 남아야 할 곳 = 로그인과 발행 버튼, 딱 두 곳.** 나머지(리서치·발상·집필·SEO·이미지·포맷·멀티채널 변환)는 자동화한다.

## 6. 레벨업 포인트 — 진짜 레버리지는 발행 버튼이 아니다

1번 초안 리서치(deep-reasoner)는 "계정정지 리스크 관리"에 집중해 7~8점짜리였다. 첫 원칙으로 다시 보면 **발행 클릭은 10초짜리 병목이지 진짜 병목이 아니다.** 진짜 병목은 소재 발굴·카피라이팅·채널별 중복노동이고, 여기를 더 파야 10점에 가까워진다.

| 추가 레버리지 | 왜 필요한가 |
|---|---|
| **원소스 멀티채널** | 소재 하나로 인스타 카드뉴스+블로그+쇼츠 대본+카카오문자 동시 생성. 블로그만 자동화하면 우선순위 1위인 인스타그램이 소외됨 |
| **공식 키워드 리서치 자동화** | 네이버 데이터랩/검색광고 API로 실제 검색량 기반 주제 선정. "감"이 아니라 데이터로 SEO |
| **성과 피드백 루프** | 발행 후 조회수·저장수를 다음 주제 선정에 반영 — 없으면 매번 제자리걸음 |
| **클라이언트별 템플릿 라이브러리** | 태권도장·이자카야·왁싱샵 등 업종별 후킹 패턴을 템플릿화 → 클라이언트 수가 늘어도 초안 품질 균일 |
| **배치 승인** | 매번 승인하지 않고 주 1회 10분에 여러 클라이언트 초안을 몰아서 승인 → 사람 부담을 "매일"에서 "주 1회"로 압축 |
| **네이버 앱 예약발행 활용** | 승인 시점에 네이버 앱 자체의 예약발행 기능으로 시간까지 지정해 발행 타이밍도 미리 끝내기 |

## 다음 단계

실제 구현으로 넘어갈 경우 Vercel Function + 텔레그램 Webhook 보일러플레이트, Claude API 연동 초안 생성 로직(원소스 멀티채널 포함), 데이터랩/검색광고 API 연동을 작성해야 한다. 이 부분은 판단이 필요 없는 기계적 작업이라 `fast-worker`에 위임하는 게 맞다.
