# 네이버 블로그 완전자동화 리서치 — Claude + 텔레그램 + Codex

## 최종 결론 (2차 재검토 반영)

**지금 규모(1인 운영, 소수 클라이언트, 주 1~2회 포스팅)에서는 텔레그램 봇·서버리스 인프라를 짓지 않는다.**
1차 리서치는 "완전 무인 자동화는 계정정지 위험 때문에 안 된다"까지는 맞게 짚었지만, 그 대안으로 제안한 봇+서버리스 파이프라인 자체가 지금 규모엔 과설계였다. 인프라가 주는 이점(스케줄링·멀티클라이언트 정리·모바일 접근)은 이미 다 대체재가 있다:

- 스케줄링 → 캘린더 알림으로 충분 (주 1~2회 빈도에서 크론은 과함)
- 멀티클라이언트 정리 → 클로드 프로젝트의 클라이언트별 커스텀 인스트럭션으로 충분
- 모바일 접근 → 클로드 앱이 이미 있음

즉 봇은 이 셋을 감싸는 껍데기일 뿐 순증가치가 거의 0이다. **진짜 병목은 "발행 자동화"가 아니라 "매주 좋은 초안을 빠르게 뽑는 것"이고, 이건 인프라가 아니라 프롬프트 자산으로 푸는 문제다.**

## 지금 채택할 최소 구성

1. 클로드 프로젝트 1개 생성 + 클라이언트별 커스텀 인스트럭션(업종, 톤, CTA 규칙)
2. 저장된 프롬프트 템플릿 — 주제 선정 → 후킹 표지문구 → 본문 → 저장유도 CTA, 원소스로 인스타 카드뉴스·블로그·쇼츠 대본·카카오문자를 한 번에 생성
3. 주 1회, 클로드 앱으로 초안을 받아서 직접 복붙 발행 (네이버 앱 예약발행 기능으로 시각 지정 가능)
4. 발행 복붙(건당 5분)은 본인이 직접 처리 — VA 위임은 온보딩·QA 관리비가 더 커서 지금은 손해

## 인프라를 다시 검토할 시점

**클라이언트 8~10개 이상 + 발행 빈도가 일 단위로 늘어날 때.** 그 전에는 텔레그램 봇/서버리스를 만들어도 매출이 아니라 유지보수(디버깅·API키 관리·배포)에 시간을 쓰게 된다. 그 시점이 오면 아래 "규모 확장 시 참고 아키텍처"를 그대로 쓰면 된다.

## 팩트 체크 (자동 발행 자체의 리스크 근거)

- 네이버 **"글쓰기 API"는 2020년 5월 6일 공식 종료**됐다. 종료 사유가 결정적이다 — 로그인 없이 워드프로세서·웹 노트에서 작성한 글을 API로 블로그에 대량 게재하는 어뷰징(광고성 블로그 양산)이 문제가 되어 서비스 시작 10년 만에 네이버가 직접 껐다. ([뉴시스](https://www.newsis.com/view/NISX20200413_0000992012), [뉴스핌](https://www.newspim.com/news/view/20200413000737))
- 즉 "자동 발행 패턴"은 네이버 FDS가 **이미 한 번 실제로 대응한 전례가 있는 타깃**이다. 브라우저 자동화로 이를 재현하면 리스크가 더 높아졌으면 높아졌지 낮아지지 않는다.
- "이메일로 포스팅" 등 우회 가능한 공식 자동화 채널은 검색으로 확인되지 않았다 — 없다고 보고 설계한다.
- 반면 **네이버 데이터랩(DataLab)·검색광고 API는 읽기 전용 공식 API로 현재도 정상 운영 중**이다. 자동화를 걸어도 되는 건 "쓰기(발행)"가 아니라 "읽기(키워드 리서치)" 쪽이다. 클라이언트 수가 늘어 리서치 자체가 병목이 되면 이 API부터 먼저 자동화 대상으로 검토한다.

## 규모 확장 시 참고 아키텍처 (클라이언트 8~10개+ / 일 단위 발행일 때)

### 왜 완전 무인은 여전히 안 되는가

- 자동 로그인 + 자동 글쓰기는 이용약관 위반이자 부정이용탐지(FDS)의 1순위 타깃. 새 기기·새 IP 로그인 시 캡차·2단계인증이 거의 확정적으로 뜬다 — 우회 대상이 아니라 사람이 개입해야 하는 지점.
- 에디터(SmartEditor ONE)는 iframe·동적 DOM이라 셀렉터가 자주 깨져 유지보수 비용이 상시 발생.
- 최악의 경우 클라이언트 계정 영구정지 → 컨설팅 사업 자체가 끝나는 사고.

### 아키텍처 옵션 비교

| 항목 | (a) 완전무인 | (b) 반자동 + 텔레그램 승인 | (c) 초안까지만 자동 |
|---|---|---|---|
| 계정정지 리스크 | 매우 높음 | 낮음 (수동 발행이라 0) | 없음 |
| 유지보수 비용 | 높음 (셀렉터 상시 깨짐) | 중간 | 낮음 |
| 실패 모드 | 캡차·정지·오발행 | 봇 다운 (치명적 아님) | 거의 없음 |
| 다수 클라이언트 확장 | 불가 (계정마다 정지위험 누적) | 가능 | 가능 |
| 사람 부담 | 0 (단, 사고 시 무한대) | 승인 1클릭 | 복붙 발행 |

**채택: (b)를 기본으로, 발행 단계만 (c)처럼 반수동 처리하는 하이브리드.**

### 텔레그램의 역할 — 단순 알림이 아니라 컨트롤 플레인

```
/포스팅 역삼효태권도장
  → Claude가 초안 생성
  → 미리보기 카드 + 인라인 버튼(발행준비 / 수정요청 / 폐기)
  → 컨설턴트 승인
  → "발행" 버튼은 자동 로그인을 트리거하지 않는다.
     클립보드/임시저장으로 넘기는 데까지만 한다.
```

클라이언트별 봇을 따로 만들 필요는 없다(과잉설계) — 채팅방/스레드 구분으로 충분하다.

### Codex CLI의 실제 역할

Codex는 실행기가 아니라 개발 도구다.

- ✅ 맞는 쓰임: 텔레그램 봇 서버, 초안 생성 파이프라인, 임시저장 보조 스크립트를 짜고 유지보수하는 코딩 에이전트로 활용
- ❌ 틀린 쓰임: Codex 에이전트가 런타임에 직접 브라우저를 몰아 네이버에 로그인·발행하는 방식 — 비결정적이고 느리고 탐지에 더 취약해서 기각

### 파이프라인

1. **트리거**: 텔레그램 `/포스팅 [클라이언트명]` 또는 Vercel Cron (배치 권장)
2. **키워드 리서치**: 네이버 데이터랩·검색광고 API로 실제 검색량 있는 키워드 자동 수집
3. **생성**: Claude API가 업종별 템플릿 + 키워드 데이터를 입력으로 주제·본문·이미지 프롬프트 생성 — 블로그뿐 아니라 인스타 카드뉴스·쇼츠 대본·카카오문자까지 원소스 멀티채널로 동시 생성
4. **초안 전달**: 텔레그램으로 후킹 표지문구 + 본문 + 저장유도 CTA 미리보기 + 인라인 버튼
5. **사람 게이트**: 컨설턴트가 검수 → 승인 (배치로 모아서 처리)
6. **반수동 발행**: 승인 시 본문을 모바일 네이버 앱 임시저장/클립보드로 전달 → 사람이 앱에서 최종 발행, 예약발행 기능으로 시각까지 지정 (정상 세션이라 FDS 안전)
7. **성과 피드백**: 발행 후 조회수·저장수를 기록 → 다음 회차 키워드/주제 선정에 반영
8. **인프라**: Vercel Serverless Functions + 텔레그램 Webhook, 상시 서버 불필요

**사람이 남아야 할 곳 = 로그인과 발행 버튼, 딱 두 곳.** 나머지(리서치·발상·집필·SEO·이미지·포맷·멀티채널 변환)는 자동화한다.

### 레버리지 체크리스트 (인프라를 지을 때 빠뜨리면 안 되는 것)

| 항목 | 왜 필요한가 |
|---|---|
| 원소스 멀티채널 | 블로그만 자동화하면 우선순위 1위인 인스타그램이 소외됨 |
| 공식 키워드 리서치 자동화 | "감"이 아니라 데이터랩/검색광고 API 데이터로 SEO |
| 성과 피드백 루프 | 없으면 매번 제자리걸음 |
| 클라이언트별 템플릿 라이브러리 | 클라이언트 수가 늘어도 초안 품질 균일 |
| 배치 승인 | 사람 부담을 "매일"에서 "주 1회"로 압축 |
| 네이버 앱 예약발행 활용 | 발행 타이밍도 승인 시점에 미리 끝내기 |

## 다음 단계

지금은 구현 착수 시점이 아니다 — 위 "최소 구성"으로 몇 주 운영해보고, 실제로 인프라가 아쉬운 지점(클라이언트 수·발행 빈도)이 생기면 그때 "규모 확장 시 참고 아키텍처"를 기준으로 Vercel Function + 텔레그램 Webhook 구현을 `fast-worker`에 위임한다.
